## Objective

Upgrade CPA-PC from CLIProxyAPI SDK `v7.1.39` to `v7.2.20`, then compare upstream changes so CPA-PC keeps its embedded single-process behavior while staying compatible with the newer SDK.

Target users:

- CPA-PC maintainers upgrading embedded CLIProxyAPI safely.
- CPA-PC management UI users who rely on the current local management console, usage pages, API-key aliases, and packaging behavior.
- Release maintainers who need a clear report of SDK and upstream management UI differences before deciding what to merge.

Core deliverables:

- Upgrade root Go module dependency from `github.com/router-for-me/CLIProxyAPI/v7 v7.1.39` to `v7.2.20`.
- Update `go.sum` and any CPA-PC integration code needed for compile/test compatibility.
- Compare upstream CPA SDK changes between the current integration baseline and `v7.2.20` using `../CLIProxyApi` as a reference source.
- Compare official management page source at `D:\develop\source-workspace\Cli-Proxy-API-Management-Center` against CPA-PC `web/` and identify relevant differences.
- Produce concise change reports for SDK changes and management UI differences.
- Directly sync relevant official management UI differences into CPA-PC while preserving CPA-PC-specific behavior.

Acceptance criteria:

- Root `go.mod` requires `github.com/router-for-me/CLIProxyAPI/v7 v7.2.20`.
- `go test ./...` passes or any failure is documented with root cause and next action.
- CPA-PC still starts as one process from `cmd/cpa-pc`; no separate `CLIProxyAPI.exe` launcher is introduced.
- Existing CPA-PC routes remain intact, including `/cpa-pc/info`, `/usage-service/*`, `/v0/management/usage*`, model prices, and API-key aliases.
- Existing embedded SDK route ownership remains intact, especially no duplicate CPA-PC `GET /management.html` route.
- A report identifies SDK changes relevant to CPA-PC: config loading, management routes, usage plugin integration, static management serving, auth, storage/runtime paths, and public API behavior.
- A report identifies upstream management UI differences relevant to CPA-PC: routes, API calls, auth handling, config editor behavior, request monitoring, model pricing, usage pages, styling/build setup, and generated asset implications.
- Reports include a clear summary of impact, newly added behavior, modified behavior, and whether any breaking changes exist.
- Relevant upstream management UI differences are synced into `web/` where compatible with CPA-PC boundaries.
- If `web/` changes, `static/management.html` is regenerated through `npm --prefix web run build`.

## Code Style

Backend changes should be minimal and keep CPA-PC integration code explicit. Prefer direct compatibility fixes over broad refactors.

Example Go style for SDK compatibility checks:

```go
func startEmbeddedCPA(ctx context.Context, cfg *config.Config) error {
	if cfg == nil {
		return errors.New("config is required")
	}

	return app.Start(ctx, app.Options{
		ConfigPath: cfg.SourcePath,
		DataDir:    cfg.DataDir,
		LogsDir:    cfg.LogsDir,
	})
}
```

Frontend changes should preserve the existing CPA-PC design system and hash router. Upstream UI code should be treated as reference material, not copied wholesale.

Example TypeScript style for API compatibility adapters:

```ts
export function managementPath(path: string): string {
  return path.startsWith('/v0/management/') ? path : `/v0/management/${path}`;
}
```

Style conventions:

- Keep changes surgical and directly tied to SDK `7.2.20` compatibility or approved UI diff adoption.
- Match existing Go formatting and TypeScript/SCSS module patterns.
- Keep user-facing frontend strings in i18n files.
- Keep generated files generated; do not hand-edit `static/management.html`.
- Do not add compatibility shims unless needed by persisted data, shipped behavior, external consumers, or SDK `7.2.20` behavior.

## Testing Strategy

Backend verification:

- Run `go test ./...` after the SDK upgrade and any compatibility fixes.
- Add focused tests only when the SDK upgrade reveals behavior changes in CPA-PC-owned logic.
- If SDK `7.2.20` changes route behavior, add or update tests around CPA-PC extra routes and management auth aliases.
- If config pass-through changes, add or update config tests covering `data-dir`, `logs-dir`, `static-dir`, `usage`, and `remote-management.secret-key` preservation.

Frontend verification:

- If `web/` is unchanged, no frontend test is required beyond documenting the upstream UI diff.
- If `web/` changes, run `npm --prefix web run type-check` and `npm --prefix web run lint`.
- If the generated management asset must change, run `npm --prefix web run build` and verify `static/management.html` is regenerated by the build script.

Manual smoke checks:

- Run `go run ./cmd/cpa-pc -config .\config.example.yaml`.
- Open `/management.html` with the example management key `123456`.
- Check that CPA-PC info, usage pages, request monitoring, model prices, config editor, and upstream management pages still load.
- Confirm management calls still use `Authorization: Bearer <management key>`.

Comparison verification:

- SDK report must identify relevant API/config/route/plugin changes from `../CLIProxyApi`.
- UI report must distinguish pure upstream differences from CPA-PC-specific customizations that should be preserved.
- Reports must include explicit recommendations: adopt now, preserve CPA-PC behavior, ask first, or ignore.

## Boundaries

Always do:

- Preserve CPA-PC as a Windows-first single-process app embedding CLIProxyAPI SDK.
- Preserve CPA-PC-specific config keys: `data-dir`, `logs-dir`, `static-dir`, `usage`, and `remote-management.secret-key: "123456"` in the example config unless an approved SDK change requires adjustment.
- Preserve `MANAGEMENT_STATIC_PATH` behavior in `internal/app` unless SDK `7.2.20` makes a documented replacement necessary.
- Preserve local SQLite usage persistence through `internal/store` and the CLIProxyAPI SDK usage plugin.
- Compare upstream sources as references, document findings, and directly sync relevant official UI changes approved by this spec.
- Run backend tests after SDK upgrade.
- Run frontend checks only if frontend source changes are made.

Ask first:

- Replacing the entire `web/` app wholesale instead of targeted upstream sync.
- Changing management routing strategy away from `createHashRouter`.
- Adding new npm or Go dependencies beyond what `go get`/`go mod tidy` requires for SDK `7.2.20`.
- Changing `config.example.yaml` semantics or removing CPA-PC-specific config.
- Committing regenerated `static/management.html` when frontend behavior did not actually change.
- Changing package targets beyond Windows amd64.
- Adding installers, Windows service behavior, or new scheduled-task behavior.
- Keeping `../CLIProxyApi` or the official management UI checkout as a long-term dependency.

Never do:

- Reintroduce a separate `CLIProxyAPI.exe` launcher.
- Add `../CLIProxyApi` or `../CPA-Manager` as subdirectories, submodules, or required runtime/build dependencies.
- Register a duplicate CPA-PC `GET /management.html` route.
- Hand-edit `static/management.html`.
- Remove or weaken management authorization.
- Move usage collection to an external HTTP/RESP queue collector.
- Delete CPA-PC custom usage pages, API-key aliases, or local persistence behavior just because upstream UI differs.
- Use live reference directories as vendored source.
